# ESQL Runtime Logging

## Overview

The ESQL runtime of opensource COBOL 4J (`CobolSql` and the internal implementation class `SqlConnection`) emits logs through SLF4J. It reports the progress of SQL operations and error information at the appropriate log levels.

Note that `CobolSql` is the public API called from the Java code generated by `cobj`, while the other classes — `SqlConnection`, `SqlCA`, `SqlCursor`, `SqlState`, `CobolDataConverter`, etc. — are all package-private internal implementations. They can be used as SLF4J logger names (fully qualified class names) in logging configuration, but are not intended to be called directly from outside.

## Log Levels

| Level | Output |
|-------|--------|
| ERROR | Error information when SQL execution fails (SQL statement, error message) |
| DEBUG | Start of SQL execution, successful connect / disconnect, cursor operations |
| TRACE | CONNECT host-variable values (user name, DB name), FETCH operations (split out because they are high-frequency) |

## Logging Sites

### CobolSql

| Method | TRACE log | DEBUG log | ERROR log |
|--------|-----------|-----------|-----------|
| `connect()` | Host-variable values (user name, DB name) | Connection successful (connection id) | Connection failed |
| `disconnect()` | - | Disconnect start (connection id) | Disconnect failed |
| `exec()` | - | SQL statement (trimmed) | SQL execution failed |
| `execWithParams()` | - | SQL statement, parameter count | SQL execution failed |
| `selectInto()` | - | SQL statement | SELECT INTO execution failed |
| `declareCursor()` | - | Cursor name, SQL statement | - |
| `openCursor()` | - | Cursor name | Cursor open failed |
| `fetchCursor()` | Cursor name | - | - |

> [!NOTE]
> `execWhereCurrentOf()` / `execWithParamsWhereCurrentOf()` have no dedicated log output, but
> because they correct the cursor position and then call `exec()` / `execWithParams()`
> internally, the `exec()` / `execWithParams()` log lines above are emitted indirectly.

### SqlConnection

| Method | DEBUG log |
|--------|-----------|
| `connect()` | JDBC URL and user name, connection successful (connection id) |

## Configuration

### Default (slf4j-simple)

`libcobj.jar` bundles slf4j-simple. By default, logs at INFO level and above are written to standard error.

To enable DEBUG logs, set the system property:

```bash
java -Dorg.slf4j.simpleLogger.defaultLogLevel=debug -cp libcobj.jar:. YourProgram
```

To enable it only for a specific class:

```bash
java -Dorg.slf4j.simpleLogger.log.jp.osscons.opensourcecobol.libcobj.sql.CobolSql=debug -cp libcobj.jar:. YourProgram
```

### Using Logback

Exclude `slf4j-simple`, add `logback-classic` to the classpath, and configure it with `logback.xml`:

```xml
<configuration>
  <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
    </encoder>
  </appender>

  <logger name="jp.osscons.opensourcecobol.libcobj.sql" level="DEBUG"/>

  <root level="INFO">
    <appender-ref ref="STDOUT"/>
  </root>
</configuration>
```

## Tests

### Unit tests

`com.github.valfirst:slf4j-test` is used for unit-testing log output. `CobolSqlLoggingTest` verifies the log level and message content of each operation.

### Integration tests

Verification of runtime logs (DEBUG/ERROR) is consolidated into the dedicated test `tests/esql-misc.src/logging.at`. This test runs, within a single COBOL program, each statement that produces a log line (CONNECT, a plain `EXEC SQL`, a parameterized `EXEC SQL`, SELECT INTO, DECLARE/OPEN CURSOR, a failing statement recorded at ERROR level, DISCONNECT) and strictly compares the runtime logs written to standard error against the expected values. Program execution uses `RUN_MODULE_LOG`, defined in `tests/atlocal.in`. `RUN_MODULE_LOG` enables the DEBUG level of the `CobolSql` logger via slf4j-simple and suppresses the bracketed display of date/time, thread name, logger name, and level so that the log lines are easy to compare against the expected values.

The other `tests/esql-*` integration tests focus on verifying the behavior of the features themselves and exclude runtime logs (standard error) from verification by marking them `[ignore]` (program execution uses the ordinary `RUN_MODULE`). As a result, even if the log format or wording changes, the only file that needs updating is `logging.at`.
